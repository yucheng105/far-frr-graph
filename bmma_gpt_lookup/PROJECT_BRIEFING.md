# 目前專案說明（從頭讀起）

這份文件是給「知道這是 Deepfake 偵測、但還沒進入 GP 公式」的人看的：專案在做什麼、現在做到哪、審查發現了什麼、以及接下來那些步驟**為什麼要做**。

更技術的公式推導在 `GP_LOOKUP_TABLE_REVIEW.md`；程式怎麼跑在 `README.md`。這份只講故事與決策。

**目前狀態：審查與說明已完成，程式碼尚未依審查結果修改。**

---

## 1. 這個專案在幹嘛

`far-frr-graph` 要做一個 **Anti-Deepfake-Box（ADB）**：一段影片進來，系統判斷它是真片還是假片。

不是只用一個模型看一次，而是把三個視覺偵測器 **排隊檢查**（cascade，串接）：

1. **SBI**
2. **Xception**
3. **UCF**

每一關不是只回「真 / 假」，而是可以回三種答案：

- 很有把握是真 → 放行
- 很有把握是假 → 擋下
- 不確定 → 交給下一關

`bmma_gpt_lookup/` 這個資料夾的任務，是把三個模型在各資料集上的表現，透過論文 **BMMA-GPT** 的幾何規劃（GP）算法，算出防禦系統真正要查的設定表：

> 在這個安全等級下，該用哪些模型、什麼順序、每關的兩個門檻各是多少。

最後產出：`output/real_data_vip_settings.csv`（Lookup Table）。

這個資料夾只**讀**外面的 `models/`、`results/`，不改那些檔案。

## 2. 先搞懂四個詞

### 分數與判定

- 分數 **0** = 真片（Real）
- 分數 **1** = 假片（Fake）
- **分數 ≥ 門檻** → 判成 Fake

門檻愈高，愈不容易被判假。

### FAR / FRR（兩種錯法）

以 `src/threshold_sweep.py` 為準：

| 指標 | 白話 | 誰算錯了 |
|---|---|---|
| **FAR** | 漏抓假片 | 假片被當成真片放行 |
| **FRR** | 錯殺真片 | 真片被當成假片擋下 |

門檻拉高 → 比較少東西被判假 → **FAR 上升**（假片更容易漏）、**FRR 下降**（真片比較不會被錯殺）。

**EER** 是 FAR 與 FRR 剛好相等的那一點，用來形容「單一模型大概有多準」。例如 FaceForensics 上：

- UCF：門檻約 0.79，FAR≈0.052，FRR≈0.05
- Xception：門檻約 0.707，FAR≈0.063，FRR≈0.057

### 雙門檻 `T_L` / `T_H`

單一門檻只有「真或假」。雙門檻多了一個猶豫區：

```text
分數 < T_L        → 判真（放行）
分數 > T_H        → 判假（擋下）
T_L 與 T_H 之間   → 不決定，換下一個模型
```

所以一定要 `T_L ≤ T_H`。若 `T_L > T_H`，規則本身是壞的。

**最後一關沒有「下一個模型」。** 最後一個檢查員不能說「我不確定」。最後一關必須只剩一個門檻，也就是 `T_L = T_H`。

### α、β、安全等級

系統整體也有兩種錯的上限：

- **α**：整條流水線的 FAR 不能超過這個（漏抓不能太多）
- **β**：整條流水線的 FRR 不能超過這個（錯殺不能太多）

目前三個等級：

| 等級 | 用意 | 至少幾關 | FAR 上限 α | FRR 上限 β |
|---|---|---|---|---|
| `fast_screen` | 快篩，愈快愈好 | 1 | 0.05 | 0.15 |
| `balanced` | 平衡 | 2 | 0.05 | 0.65 |
| `forensic` | 鑑識，多層防禦 | 3 | 0.3 | 0.6 |

`forensic` 的 α 比較鬆（0.3），不是打錯字：三關疊在一起時，目前這三個模型不夠準，α 太嚴會解不出合法門檻。這組數字是依**現況**校準的，模型或合併方式一改，就要重校。

### GP / conb（為什麼需要計算機）

每關兩個門檻、還有 15 種排隊順序，不能手調。論文把問題寫成幾何規劃（GP），讓 cvxpy 自動解。

為了讓數學能解，論文假設每個模型大致遵守：

```text
FAR × FRR  ≈  一個常數 conb
```

`conb` 愈小，模型愈好。GP 不直接解門檻數字，而是解每關的錯誤率 `AB`（對應 FAR）、`RB`（對應 FRR），再反查回真正的 `T_L`、`T_H`。

## 3. 程式現在怎麼走（四步）

主程式是 `build_lookup_table.py`。

1. **讀資料**：把 SBI / Xception / UCF 在 CelebDF、DFDC、FaceForensics 上的 threshold sweep 讀進來，合併成每個模型一條 FAR/FRR 曲線，算出 EER、conb、平均延遲。
2. **窮舉順序**：1～3 關所有排列，共 15 種。
3. **GP 求解**：對每個順序，在「系統 FAR ≤ α」的前提下，最小化系統 FRR，得到各關的 `AB_lb`、`AB_ub`。
4. **篩選並反查**：依安全等級的 α、β、延遲預算、最少關數挑一個順序，把 `AB` 反查成真正門檻，寫進 Lookup Table。

已知資料雷區：`models/sbi/` 的 FaceForensics sweep 欄位寫反過，所以 SBI / FF++ **必須**用 `bmma_gpt_lookup/threshold_sweep_sbi_faceforensics_v1.csv`。

另外：數學上，多關串接的 GP 上界 **不可能低於** 單一最好的那個模型。所以若沒有 `min_stages`，系統永遠只會選「單獨用 UCF」。多層防禦是政策，不是因為三關數學上更準。

## 4. 現在已經有什麼、問題在哪

已經能跑、已經有輸出：

- `output/real_data_vip_settings.csv`：三個安全等級各選了一條路徑
- `output/all_orderings.csv`：15 種排列的診斷表
- `validate.py` 會檢查 `T_L < T_H` 這類格式

**但這張表現在不能當成「上線就用的正確設定」。** 審查發現 GP 解的問題，和防禦系統真正在跑的問題，不是同一題。

最容易看懂的證據：`fast_screen` 選了單獨 UCF，門檻卻是

```text
T_L = 0.05
T_H = 0.775
```

中間一大段影片，最後一關（也是唯一一關）會說「不確定」。沒有下一關。公式卻幾乎沒把這些猶豫算進錯誤率，所以表上寫 `total_far ≈ 0.0004`，看起來極準，實際上是計算機鑽了漏洞。

## 5. 接下來為什麼要做那些事

下面每一步都是在修「計算機解的題」和「系統真正在跑的題」之間的落差。不是為了改而改。

### 為什麼要修 GP 語意？

**最後一關 `AB_lb == AB_ub`（也就是 `T_L = T_H`）**

想像安檢有兩種按鈕：放行、擋下、以及「請下一位同事看」。最後一位同事沒有下一位。如果還給他「不確定」按鈕，優化器會故意讓他狂按不確定：公式只對明確放行收 FAR、只對明確擋下收 FRR，猶豫等於免費。

加上「最後一關兩個錯誤率必須相等」，等於強迫最後一人必須給答案。這才是論文與 `progress_report.md` 裡的 cascade。

**加上 `RB ≤ 1`（等價 `AB ≥ conb`）**

`RB` 是「真片被拒絕」的機率，必須介於 0 和 1。現在沒卡這條，計算機可以把某個數設成 32，再乘到後面幾關，於是表上出現 `total_frr = 5.88`（588% 的人被錯殺）。那不是真的錯殺這麼多，是機率乘積已經不是機率。

**為什麼這步之後 α = 0.05 可能暫時無解？為什麼不要先放寬 α？**

α = 0.05 的意思是：整條線漏抓假片不能超過 5%。  
加上「機率必須像機率、最後一關必須給答案」之後，以**現在被灌水的 conb**，這三個模型可能達不到 5%。

這時有兩種反應：

- 錯的：把 5% 改成 30%，讓表又「有解」——等於尺子壞了，先把及格線畫近一點。
- 對的：先承認「用現在這把尺子，5% 達不到」，下一刀去修尺子（合併資料的方式），再來看 5% 够不够。

所以「暫時無解」是診斷結果，不是要你立刻把 α 放寬。

### 為什麼要修反查？

GP 解出來的是錯誤率（例如「這一關 FAR 要 0.02」），系統要的是門檻（例如 0.63）。需要從曲線反查。

現在下界用 FAR 曲線查 `T_L`、上界用 FRR 曲線查 `T_H`。這兩條路只有在 `FAR × FRR` 幾乎等於同一個常數時才會對上。目前 conb 是「所有點裡最大的那個乘積」，是偏高的上界，不是逐點等式。於是 `T_H` 被往左拉，出現 `T_L > T_H`（下門檻比上門檻還高，規則壞掉）。三關在 α=0.05 時，診斷表上 6 種排列全部非法。

**兩邊都改用 `inv_far`：** FAR 隨門檻上升是單調的。GP 保證下界 FAR ≤ 上界 FAR，反查後自動 `T_L ≤ T_H`。這保證的是「門檻順序合法」。在 conb 仍是上界的前提下，真實 FRR 只會 ≤ 計算機宣稱的值，β 不會被偷偷放寬。

**clip 當失敗：** 現在若計算機要一個曲線上不存在的 FAR（例如 0.000001），程式默默夾到曲線最小門檻 0.05，看起來像解出來了。那是假裝有解。應該標成失敗。

**用差式 cascade 重算再寫 CSV：** 表上現在印的是 GP 代數值，不是這對門檻真正拿去排隊檢查時會量到的 FAR/FRR。Lookup Table 是給防禦系統用的，應該寫「落地後量得到的數字」，不是「優化器目標函數的值」。

### 為什麼要修 combine？

三個資料集（CelebDF、DFDC、FaceForensics）表現差很多。FF++ 上 UCF 的 EER 約 5%；CelebDF/DFDC 差很多。

現在的合併是：同一個門檻，各資料集的 FAR 取最大、FRR 也取最大，再拼成一條曲線。可能發生：

- 資料集 A 在某門檻：漏很多、但很少錯殺
- 資料集 B 在同一門檻：很少漏、但錯殺很多
- 拼出來：又漏很多、又錯殺很多 → **沒有任何真實資料集這麼差**

這條假曲線讓 conb 從「FF++ 上約 0.0025」被灌成「0.137」。GP 以為模型很爛，門檻才會那麼緊、forensic 才需要 α=0.3。

改成「選 conb 最差的**整條**資料集曲線」：仍然保守（用最難的那個世界），但不會製造一個不存在的模型。尺子修好後，再回頭看 α=0.05 能不能解——這才是放不放寬 α 的時機。

### 為什麼要重校 SECURITY_LEVELS？

`fast_screen` / `balanced` / `forensic` 的 α、β 是用**舊模型、舊漏洞、舊 conb** 試出來「剛好有解」的數字。前面三刀任一刀都會改變「什麼叫有解」。

舊的 forensic α=0.3 不能當真理帶去新模型。要等 GP 語意、反查、合併都修完，用新的診斷表重看：各等級實際能達到的最小 FRR 是多少，再設 β；α 是否仍需 0.3 以新數字為準。

然後才重跑、重產 `real_data_vip_settings.csv`。那才是下一張「可以拿去討論上線」的表。

### 為什麼期望延遲和 test set 要之後再說？

**期望延遲：** 現在表上叫 `expected_latency_ms`，其實是「三關都跑完」的最壞時間加總。真正的期望時間要算「有多少人會被送到第 2、3 關」。那一步要用真實門檻與續傳機率，**不能**塞進 GP：續傳機率是兩個數相減，幾何規劃不收這種式子。先讓門檻是對的，再算時間才有意義。

**獨立 test set：** 現在用來調門檻的 sweep，不能跟最後報成績的測試集重疊，否則分數會虛高。這是上線評估，不是修 GP 漏洞。腳本開頭已有警告。現在表的語意還不對，先評估沒有意義。

## 6. 建議的工作順序（對照「為什麼」）

| 順序 | 做什麼 | 不這樣會怎樣 |
|---|---|---|
| 0 | 跟寫 GP 的人對齊：最後一關必須給答案；conb 是上界 | 改 code 改到一半又為了「有解」把約束拿掉 |
| 1 | 修 GP：最後一關單門檻 + 機率 ≤ 1 | 表上的 FAR/FRR 可以靠「不回答」變好看 |
| 2 | 修反查：兩邊 `inv_far`、clip 當失敗、重算真實錯誤率 | 門檻交叉，或 CSV 數字對不上實際系統 |
| 3 | 修合併：最差改選整條資料集 | conb 被假曲線灌水，α=0.05 看起來永遠達不到 |
| 4 | 重校 α/β，重產 Lookup Table | 拿舊及格線去套新尺子 |
| 5 | 期望延遲、獨立測試集 | 門檻還不對就先做這些，數字無法解釋 |

現在**不要**做的：

- 為了三關「有解」去把 conb 改成 EER²，或再把 α 放寬
- 把現有 CSV 的 `system_total_far` / `system_total_frr` 當成真實系統表現
- 把期望延遲寫進 cvxpy
