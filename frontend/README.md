# 前端開發說明

這份文件給負責畫面的人。網站不訓練模型、不跑 GP、不跑 MILP。偵測器分數與查表都在離線算完，前端只讀 CSV，讓使用者選架構與安全等級，看系統會用哪一組設定、漏抓與誤擋各是多少、一支部影片是在哪一關被決定的。

## 系統在做什麼

一段影片進來，三個偵測器各自給出 0 到 1 的分數，愈高愈像偽片。

- **串聯**：偵測器排隊。分數低於下門檻判真，高於上門檻判偽，中間才送下一關。最後一關沒有下一關，所以上下門檻必須相等。
- **平行**：三個偵測器同時算，加權得到一個總分，再和一個總門檻比較。

兩種架構都先在離線做成查表。使用者選定「偽片被放行的上限」之後，畫面查出該用的順序、門檻或權重。

## 畫面上使用的 FAR／FRR

與 `far-frr-relation/src/threshold_sweep.py`、平行式 MILP 相同：

- 標籤 `0` 是真片，`1` 是偽片。
- **FAR** = 偽片被判真的支數 / 偽片支數。
- **FRR** = 真片被判偽的支數 / 真片支數。

分母是該類別的支數，不是「系統判成接受的支數」或「系統判成拒絕的支數」。10/8 簡報若寫成 falsely accepted / accepted，那個分母和現有 CSV 不同，前端不要自行換算。CSV 裡的 `far`、`frr` 直接顯示，並在頁面上用上面這兩句話標明定義。

同時顯示分子與分母，例如 FAR `28/560 = 0.050`。資料集小時，比率差 0.01 可能只是幾支影片。

## 頁面結構

單頁，由上到下六塊。桌面寬度約 1100px 置中；手機時結果卡改成直向堆疊，表格可橫向捲動。

### 1. 標題與一句話

標題：深偽偵測融合查表。

副標：在指定的漏抓上限內，查出該用哪些偵測器、什麼順序或權重。

旁邊列出三個偵測器與延遲（毫秒）。數字來自查表，不寫死在程式裡。目前量測尚未統一是否含人臉偵測與對齊，延遲旁加註「量測協定待補」。

### 2. 操作區

兩個控制項：

| 控制項 | 選項 | 作用 |
|---|---|---|
| 資料集 | FaceForensics++、Celeb-DF-v2、DFDC | 換一張查表。三個資料集的難度差很多，不混成一個數字 |
| 架構 | 串聯、平行 | 換查表檔 |
| 安全等級 | 快速篩檢、平衡、鑑識 | 查出該等級的一列設定 |

安全等級底下用白話寫出這一列的 FAR 上限，例如「偽片被放行不超過 5%」。上限來自 CSV 的 `far_limit`，不在前端寫死 0.05。

選完後顯示結果卡：

**串聯**

- 順序，例如 UCF → Xception → SBI
- 每一關的偵測器、下門檻、上門檻
- 最後一關兩個門檻必須相同；若 CSV 違反這條，結果卡顯示「查表不合法」，不要畫成正常流程
- 系統 FAR、FRR（含分子分母）
- 期望延遲、最壞延遲
- `split` 欄位：這組數字是在驗證集上擬合，還是在測試集上量到的

**平行**

- 三個權重與總門檻
- 加權分數的公式：`q = αX·Xception + αU·UCF + αS·SBI`，`q ≥ β` 判偽
- 三個偵測器都會跑，延遲顯示最慢的那個
- 系統 FAR、FRR、求解狀態
- `optimal` 為假時，標成「時間內找到的可行解」，不要寫成「最佳解」

某一等級沒有列時，結果卡寫「這個 FAR 上限在這個資料集沒有合法設定」，並自動帶出同一張表裡下一個有解的等級。不要沿用舊的 `bmma_gpt_lookup/output/real_data_vip_settings.csv` 填空。那張表把三個資料集拼在一起，而且 `expected_latency_ms` 目前仍是各偵測器自己的耗時，不是期望延遲。

### 3. 取捨曲線

橫軸 FAR 上限，縱軸 FRR。同一資料集畫兩條線：串聯、平行。使用者選到的點高亮。

資料來自查表裡每一個 `far_limit` 的那一列，不是前端自己重算。沒有那個上限的點就空著。

### 4. 單支影片怎麼被判

用下拉選單從「範例清單」選一支已經有三個偵測器分數的影片。真片與偽片都要有。第一版不做檔案上傳，也不在瀏覽器跑模型。

**串聯**：依結果卡的順序逐關顯示分數、落在判真、判偽或續傳。判真或判偽就停止，並標出最終決定發生在第幾關。

規則：

- 分數 < 下門檻 → 判真
- 分數 > 上門檻 → 判偽
- 兩者之間 → 下一關
- 最後一關上下門檻相同：分數 < 門檻判真，否則判偽

**平行**：顯示三個分數、加權後的 q、β，以及 `q ≥ β` 則判偽。

最後一行寫地面真偽、系統判決、若判錯則標 FAR 或 FRR。

### 6. 尚未完成

固定短文，避免展示時被看成已上線產品：

- 查表仍可能是在同一批分數上擬合，跨資料集測試要等切分完成才填第二張表
- SBI 很慢，串聯應盡量把它放在後面；它是否含前處理，延遲協定尚未統一
- 混合式（每一級裡再做平行）尚未做
- 不能上傳任意影片

## 畫面行為

1. 開啟頁面時讀取五個 CSV。任一檔讀取失敗，只讓用到該檔的區塊顯示錯誤，其他區塊仍可操作。
2. 預設資料集 `FaceForensics++`、架構「串聯」、等級「平衡」。若該組合沒有列，改選該資料集第一個有解的等級。
3. 切換資料集、架構、等級時，結果卡、曲線高亮、範例影片的逐關過程一起更新。範例清單只留目前資料集的影片。
4. 門檻與權重顯示到小數點後三位。FAR、FRR 顯示到小數點後三位，並附分子與分母。
5. 延遲顯示毫秒，整數即可。同時出現期望值與最壞值時，兩個都留，並註明期望值是「平均會跑到幾關」，最壞值是「每一關都跑」。
6. 顏色只表達狀態：有解、無解、判對、判錯。不要用顏色單獨區分真偽，旁邊要有文字。

## 建議的做法

用一個靜態頁面即可，不必接後端。

- 用 Vite 起一個小專案，放在這個 `frontend/` 資料夾。
- 畫面用一般 HTML 與 CSS。CSV 用 `fetch` 讀取後以 Papa Parse，或自己拆行。
- 曲線可用一張小型圖表套件。只有兩個序列、十幾個點，不要為了圖表再加一套狀態管理。
- 部署時整個 `dist` 就是靜態檔。查表更新時，替換 `public/data/` 裡的 CSV 再重新建置。

第一個可以演示的版本，只要第 2 塊結果卡能依 CSV 切換。曲線、範例影片、比較表依序補。沒有 CSV 的區塊留空狀態，不要先畫設計稿上的假數字。

## 不在前端做的事

- 不呼叫 cvxpy、HiGHS，不在瀏覽器解 GP 或 MILP
- 不載入 Xception、UCF、SBI 的權重
- 不把三個資料集的 FAR 平均成一個總分
- 不在頁面上修改門檻再宣稱那是查表的最佳解。若之後要做「手動調門檻看 FAR 變化」，必須另外標成「試算」，並且用同一支評估函式重算，不能沿用查表上的舊 FAR
